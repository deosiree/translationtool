## 原型转真实代码实现规划（回写按钮 & 回写前校验）

> 目标：在保持当前原型交互体验的前提下，将 `prototype/writeBackValidate` 下的原型代码，分阶段、安全地迁移为正式可上线代码，并与实际词条管理业务、Git 工作流打通。

---

### 一、范围与对象

- **页面 / 组件范围**
  - `PrototypePage.vue`：原型整体容器页，承载回写相关场景。
  - `writeBackButton.vue`：回写入口组件（按钮 + 配置弹窗 + 回写前校验入口）。
  - `WriteBackValidateModal.vue`：回写前校验弹窗（展示重复组、删除 / 软删等操作）。
  - `createVersionModal.vue`：与版本创建 / Git 推送相关的交互原型（如有）。
  - `mockUtils.js`：原型阶段的 mock 数据与模拟行为。
- **业务功能范围**
  - 选择 IP、回写语种、多语言回写。
  - 区分回写类型：默认 / TS 文件 / 辞典。
  - 可选的“回写前校验”流程。
  - 回写后可选 Git 提交 / 推送。
  - 原型模式（`isPrototype = true`）与真实模式（`isPrototype = false`）的差异行为。

---

### 二、总体阶段规划

1. **阶段 A：原型代码盘点与差异分析**
   - 梳理原型内所有 “mock 行为 / 演示专用逻辑 / 控制项”。
   - 对比 `src/views/entry/productEntry.vue` 等真实业务页面的现状，识别：
     - 已有的回写/导出/校验相关逻辑。
     - 状态管理（store）、接口定义（`@/http/api` 系列）、公用工具（`@/utils`）中已有的能力。
   - 输出一份「差异清单」：原型有但正式页没有的功能点，以及交集部分的差异。

2. **阶段 B：接口和数据流设计统一**
   - 明确正式环境下回写的 **真实接口协议**：
     - 回写接口 `writeBack` 的入参 / 出参、错误结构。
     - 获取 IP / 分支 / TS 文件列表 / 辞典列表等接口参数。
   - 校对 `writeBackButton.vue` 中构造的参数对象（`buildWriteBackParamsList`、`executeWriteBack` 中的 `rows`、`selectedKeys` 等）是否与真实接口一致。
   - 统一「词条业务数据结构」：确认 `dataSource` 中的核心字段（如 `id`、多语言内容、状态）与现网保持一致。

3. **阶段 C：原型模式与真实模式的切换策略设计**
   - 保留 `isPrototype` 属性，但仅用于 **开发 / 演示环境**：
     - 原型模式：使用 `mockUtils.js` 中的 mock 方法 + 强制“成功 / 失败”分布逻辑。
     - 真实模式：完全走真实接口，无随机干预。
   - 设计切换策略：
     - 配置维度：通过环境变量 / 构建配置自动注入 `isPrototype` 默认值。
     - 组件维度：上层页面传入 `:isPrototype`，联动校验弹窗等子组件。

4. **阶段 D：组件行为与交互规范化**
   - 明确 `writeBackButton` 的两种使用模式：
     - `mode="button"`：自带按钮 + 弹窗（业务页面简单集成）。
     - `mode="modal"`：完全受控弹窗（由上层控制打开 / 关闭）。
   - 明确 `submitMode` 的两种行为：
     - `"writeBack"`：内部直接完成回写 + （可选）git 提交 / 推送。
     - `"emit"`：仅校验表单 / 参数，校验通过后将参数和数据抛给上层，由上层决定是否回写、如何回写。
   - 设计上层页面（如 `productEntry.vue`）的集成方式：
     - 在「词条选中区域」附近增加 `writeBackButton`。
     - 使用 `dataSource` 明确传入当前选中的词条集合。
     - 根据业务需求选择 `submitMode` 与 `enableValidation`。

5. **阶段 E：回写前校验流程落地**
   - 基于 `WriteBackValidateModal.vue` 原型：
     - 设计真实的校验接口 / 规则（重复组识别、软删 / 硬删）。
     - 明确校验结果与 `dataSource` 的映射关系（删除 / 去重后如何回写到父组件）。
   - 优化数据流：
     - `writeBackButton` 在 `emit` 模式下，使用 `@update:dataSource` 对父组件进行统一的数据更新。
     - 校验弹窗内部所有对数据的修改，均通过事件向外抛出，避免多处维护同一状态。

6. **阶段 F：Git 提交 / 推送流程打通**
   - 对齐 `doCommitAndPush` 的真实实现：
     - 确认需要的参数（IP、分支、版本名等）。
     - 处理失败 / 超时 / 权限不足等异常情况。
   - 将原型中的 `mockGitCommit` / `mockGitPush` 封装到 `mockUtils.js` 中，统一管理，并在非原型环境彻底禁用。

7. **阶段 G：代码整理与复用抽取**
   - 按你提供的“代码重构最佳实践规则”：
     - `methods` 分组注释已经初步按生命周期 / 数据加载 / 表单校验 / 执行回写 / 校验弹窗事件划分，后续保持一致风格。
     - 识别可抽取的辅助方法：
       - 参数构建（如 `buildWriteBackParamsList`）。
       - 校验通用逻辑（校验 IP / 语言 / 分支等）。
       - Git 操作包装（commit + push 封装）。
   - 将可复用逻辑沉淀到 `@/utils` 或专用 service 层，减少未来其它页面接入回写功能的成本。

8. **阶段 H：联调、自测与回归**
   - 在开发环境：
     - 使用原型模式验证交互流畅性、信息提示完整性。
     - 切换到真实模式，联调回写接口、校验接口、Git 接口。
   - 在测试环境：
     - 用典型场景覆盖：
       - 单语言 / 多语言回写。
       - TS 文件 / 辞典 / 默认模式。
       - 开启 / 关闭“回写前校验”。
       - 不同 Git 分支 / 不同版本名。
   - 回归 `productEntry.vue` 原有功能，确保引入回写模块不会破坏原有导入 / 导出 / 过滤等逻辑。

### 三、关键设计决策点（需要在实现前确认）

1. **回写前校验的定位**
   - 是“强制步骤”（必须先校验才能回写），还是“可选工具”（仅在风险高场景启用）？
   - 校验中的“删除 / 去重”操作是对真实数据生效，还是仅影响本次回写的数据集？

2. **Git 流程与权限**
   - 谁有权限触发 commit / push？
   - commit message 与版本命名（`userName-versionName`）是否需要对齐研发规范？
   - push 失败时如何回滚 / 重试，如何向用户反馈？

3. **多语言回写的一致性**
   - 回写是“全部成功才算成功”，还是“允许部分成功、部分失败”？
   - 部分失败时，是否需要记录审计日志或导出失败详情供运维 / 开发排查？

4. **原型模式的去留策略**
   - 是否长期保留原型页 `PrototypePage.vue` 作为“演示 / 培训用”页面？
   - 还是在功能完全上线后，删除原型页，只保留正式页面中的回写入口？
